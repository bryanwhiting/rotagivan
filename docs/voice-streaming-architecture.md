# Voice live-candidate architecture

Verified against public primary-source documentation on 2026-09-26. This is an architecture proposal, not a claim that streaming voice is implemented or installed. Research used no credentials or inference calls.

## Published Jev contract

OpenRouter documents `POST https://openrouter.ai/api/alpha/decisions` with model `typesafe/jev-1.13`, `state`, and named `questions`. The documented response is a complete `application/json` decision result. Its schema has no streaming option or SSE/WebSocket event protocol. `session_id` is observability grouping metadata, never forwarded to the provider—not a persistent inference session. [Decisions API reference](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request)

For a Choice question, `criteria` maps option IDs to descriptions; the answer is returned under the request's question ID. `choice` identifies the highest-probability option, while `probabilities` covers every option and sums to one. Top three is a client-side ranking, retaining the original probabilities. Supply an explicit `none` option for unrelated/incomplete speech: there is no documented native `no_match` field. Choice supports up to 255 options, including that sentinel. [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice)

`confidence` measures the shape/concentration of the distribution, not the winning option's probability or guaranteed accuracy. Calibrate thresholds using representative commands and action risk; do not relabel confidence as probability. [TypeSafe confidence](https://docs.typesafe.ai/confidence)

TypeSafe's SDK exposes a promised `systemOne` result and per-call cancellation, retries, and timeout; those references do not document incremental decision events. Therefore Jev-specific streaming/session reuse remains **unverified**, rather than proven impossible. OpenRouter's general chat streaming support is not evidence for this decision endpoint. [TypeSafe client](https://docs.typesafe.ai/sdk/javascript/api/classes/TypeSafeClient), [request options](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RequestOptions)

## Transcription is a separate transport

Current `Rotagivan/VoiceActions.swift` posts a completed WAV to OpenRouter `/api/v1/audio/transcriptions` using `x-ai/grok-stt-1.0`, then classifies the returned text. OpenRouter documents base64 audio-upload transcription returning JSON; that contract does not establish a realtime WebSocket or partial-transcript service. Its mention of large-file streaming offload is not a partial-transcript event protocol. [OpenRouter STT documentation](https://openrouter.ai/docs/guides/overview/multimodal/stt)

xAI separately documents direct `wss://api.x.ai/v1/stt`: binary audio frames, JSON transcript events, and partial results when enabled, authenticated with an **xAI** key. This is not the OpenRouter upload endpoint or an OpenRouter-key feature. Adopting it requires an explicit provider/credential/product decision, including direct native transport versus a backend proxy; never send an OpenRouter key to xAI or silently substitute/fall back. Jev itself accepts text, not native audio. [xAI streaming STT reference](https://docs.x.ai/developers/rest-api-reference/inference/speech-to-text), [Jev model input contract](https://openrouter.ai/typesafe/jev-1.13)

## Proposed bounded live candidate updates

Keep transcription and classification distinct: a supported partial-text source feeds independent, complete Jev snapshots. Reuse HTTP connections for efficiency, without claiming provider inference-state reuse.

The default OpenRouter fallback can refresh provisional candidates using repeated bounded WAV uploads; it remains snapshot polling, not true audio streaming. The next implementation must retain provisional updates rather than become final-only. Current gaps to close are final work blocked behind partial work, failure leaving credential preparation able to resume, a final latch checked after candidate mutation, and no whole matching deadline across batches. Separately, proposed strict latest-transcript filtering risks starving previews during continuous speech. Treat these as implementation acceptance gates, not fixes delivered by this document.

1. Debounce meaningful transcript changes. For the existing upload fallback, admit one serial STT→Jev work unit plus one replaceable latest-pending audio snapshot. For true streaming STT, separately bound one transcript producer and one classification request plus one replaceable latest-pending text snapshot—never a backlog per audio chunk.
2. Each snapshot captures transcript revision, session generation, catalog revision, and active application scope. Publish completed provisional revisions monotonically while listening, even when newer work is pending, so continuous speech does not starve previews. Reject invalid session/catalog/scope results, backwards revisions, and previews superseded by the final latch. Check that latch before mutating candidate state.
3. Finalization immediately supersedes pending previews and cancels superseded work. For upload fallback, this happens when final audio is captured—not after final transcription returns—then the final STT→Jev work receives priority once the admitted operation drains. Streaming STT similarly prioritizes final text. Do not release admission merely because the UI stopped awaiting it; release only after transport completion/cancellation is acknowledged. Never allow preview and final pipelines to overlap unboundedly.
4. Apply one monotonic overall matching deadline, including drain, requests, and retries; guard its timer by generation and attempt. On timeout/error/cancel, stop the microphone, invalidate results and preparation immediately, clear stale executable selection, and report failure. Retain admission during asynchronous transport drain without blocking normal quit. If drain stalls, remain failed/occupied: retry needs a free slot or an actionable busy error, never a second pipeline. Give all transports a cancellation/drain/close contract rather than relying on a concrete OpenRouter downcast.
5. Preview results only update ranked candidates; partial text never executes an action. Final transcript classification supports manual confirmation by default. Preserve existing explicitly enabled AutoDecide behavior as a once-only final decision, subject to the same validation and safety gates—not provisional automatic execution.
6. Immediately before execution, revalidate the original matched record against the current registered action, enabled state, and application scope. Stable IDs alone do not authorize an edited action. Unknown IDs, `none`, malformed distributions, stale generations, or failed revalidation fail closed.

Offline acceptance tests should cover coalescing, final priority, cancellation drain, overall deadline, late responses, restart, scope switches, edited/removed actions, and malformed/unknown-option responses. Provider streaming support needs a documented Jev endpoint/event schema or explicit provider confirmation before a native Jev-stream implementation is proposed.
